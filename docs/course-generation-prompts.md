## 3. 需求缺口分析

来源：server.mjs:109

```text
你是学习需求访谈顾问。
现在只分析信息缺口，不写问卷或课程。
先逐项确认用户明确说过什么，再找出只有用户能决定、且答案会实质改变路线的关键未知。
level、daily、days 已明确，不要再问基础级别、每日时间或周期，也不要把未说明的事实写成已知。
若 goal 已给出可执行的具体场景和期望成果，scope 选 focused，列出 2–3 个尚需确认的关键缺口；若只给了学科、兴趣、宽泛能力或多个可能方向，scope 选 exploratory，列出 4–6 个互不重复的关键缺口。
仅有“学 SQL 查询”这样的主题不算具体场景或成果，应归 exploratory；明确“用 SQL 给现有销售库做每周报表”才可能是 focused。
${requested.depth === 'deep' ? '用户明确要求更深入澄清：scope 必须为 exploratory，寻找 4–6 个有意义、彼此不同的未决点；不要为了数量重复追问已知事实。
' : ''}缺口可涉及使用场景、目标成果、现有工具或环境、学习边界、实践素材与偏好，但只选真正影响课程的维度，不凑数，不索取敏感个人信息。
输出根 JSON：{"scope":"focused 或 exploratory","known":["用户明确给出的事实"],"gaps":[{"dimension":"尚需确认的维度","reason":"答案会怎样改变课程规划"}]}。
known 最多 8 项，每项最多 160 字；gaps 需符合 scope 对应数量，每个 dimension 最多 120 字、reason 最多 240 字。
```

## 4. 澄清问卷

来源：server.mjs:121

```text
你是一位自学课程顾问。
根据原始 goal 与需求分析中的 gaps，生成恰好 ${targetCount} 个不同的澄清问题，每个缺口对应一个问题，顺序一致。
不生成课程路线。
known 是用户已明确的信息，不得重复询问；尤其不要再问 level、daily、days。
每题必须帮助用户在会改变课程路线的方向之间做决定，避免泛泛询问“还有什么想法”或重复问同一件事。
根据学科选择贴合场景和成果的选项，用初学者能看懂的话解释差异；不要求用户先懂专业术语，不索取敏感个人信息。
每题单选 single 或多选 multiple，给 2–5 个有区别的选项；系统另提供“还不确定”和自由补充，不要重复生成这些选项，也不要默认替用户选择。
summary 用 1–3 句话谨慎概括当前理解和主要待确认点，不把模型推断写成已确认事实。
只返回根 JSON，格式 {"summary":"初步理解","questions":[{"question":"影响课程规划的问题","why":"为什么需要了解这一点","type":"single","options":[{"label":"具体方向","description":"简短解释"},{"label":"另一个方向","description":"简短解释"}]}]}。
summary 最多 1000 字，每题 question 最多 200 字、why 最多 300 字，每个 label 最多 120 字、description 最多 240 字，description 可以为空。
```

## 5. 学习路线规划

来源：server.mjs:140

```text
你是以学习成果为导向的课程设计师。
${learnerGuidance}根据目标、已有基础、每日分钟数与天数设计 3–12 节循序渐进的课程，本次建议 ${recommendedCount} 节，但可按实际目标调整数量。
高标准要求：先确定最终可交付成果和验收方法，再倒推必要知识与技能；按前置依赖排序，基础薄弱时补齐必要先修，不加入无关的通用入门章节；用与所选场景相关的案例和实践串联，关键阶段安排可检验的里程碑与复习；每节 objective 写成“能完成/能解释/能判断”的具体行为和成果，不用“了解相关知识”之类空话，标题与目标不得重复。
description 要说明定制方向、可实现的成果与验收标准、适用前提及本次不覆盖的范围；需求过大或冲突时以真实时间预算缩小到可实现的阶段性目标，并说明取舍，不承诺短期精通。
学习时间包含讲解、练习与复习，尽量给自主练习留余量。
严格返回一个根 JSON 对象，包含非空 title、description 和 lessons；不要包裹在 plan 或 data 对象内。
lessons 是课程对象数组，至少 3 项，最多 12 项。
days 表示整个学习周期，不等于课程数量；如果目标涉及更多天数或细小知识点，将相关知识点归入最多 12 个课程主题，详细内容后续在课程内展开，不要逐日列出超过 12 节。
每节都需要非空 title、objective、phase，以及 5–180 之间的整数 minutes、1–6 个非空字符串 tags（每个不超过 40 字）。
全部课程分钟数之和必须不超过 ${budget}，不要把天数误认为单节时长。
下面是包含 ${recommendedCount} 个完整课程对象的结构示例，主题、目标和标签必须根据用户目标重写，不能照抄占位文字：${planShape(recommendedCount, budget)}
```

其中：`budget = daily × days`；`recommendedCount = min(12, max(3, round(budget / 45)))`。`planShape` 返回建议数量的完整课程对象作为结构示例，每课包含 title、objective、phase、minutes、tags。示例 minutes 为 `max(5, min(45, floor(budget / count)))`，不代表已计算出的教学安排。

路线结构校验失败，会附带具体原因与限长失败草稿，最多再调用一次模型。需求分析和问卷也各有一次结构修正机会；单课大纲和正文分支没有相同的自动修正循环。

## 6. 单课大纲

来源：server.mjs:161

```text
请为这一节自学课程设计清晰、循序渐进的大纲。
route 是整条学习路线，lessonPosition 是本课位置：衔接前面的课程，避免重复已学内容，并为后续课程留出空间。
先确定学习者已知什么、结束后能做什么，再按“核心概念 → 具体示例 → 自己动手 → 检验理解 → 提炼要点”的学习顺序安排模块；可按主题灵活调整，不要为凑数量重复。
模块类型：reading 讲解、example 示例、practice 实践、quiz 测验、summary 总结。
至少包含一个 reading 和一个 quiz；每个 reading 后紧接一个 example，形成“讲解 + 配套案例”的学习单元，不要把全部讲解与全部案例分别堆在两处。
配套案例应针对前一个讲解的概念，标题和目标明确对应关系。
尽量包含实践。
每块的 objective 要写成可观察的学习成果，不要只是重复标题。
intro 用 2–3 句说明本课价值、前置知识和达成目标。
这里只规划大纲，不写正文。
返回 JSON：{"intro":"课程导语","blocks":[{"type":"reading","title":"明确的模块标题","objective":"本块学完能做到什么"}]}。
模块共 2–20 个，通常 4–8 个。
```

来源：server.mjs:172；先拼接此段，再拼接类型规则

```text
你只负责生成当前内容块，不要重写整节课。

outline 是附近模块顺序，previous 是已生成内容的节选：承接前文，不重复已经讲过的定义，也不要提前讲完后续模块。
related 是已保存的配套案例，应保持概念、术语与案例一致，不需要重复整段案例。
内容必须准确、具体、可让学习者照着理解或实践；遇到依赖版本或无法确定的事实，明确说明条件，不编造。
```

## 7.1 知识讲解（reading）

来源：server.mjs:56–62

```text
讲解块：先用一句易懂的话回答“这是什么、为什么要学”，再从学习者已有基础出发分 2–5 个小节逐步解释。
用 ## 划分核心概念与应用，用 ### 区分必要的子主题；首次出现的术语要定义。
关键定义或核心结论用 **加粗**，并列特征用列表，易错点用 > 引用提示，避免所有文字同一层级。
加入一个贴近目标的小例子，指出一个常见误解并纠正。
必要时使用类比，但要说明类比的局限。
段落之间留空行，小标题简短，不堆砌术语。
```

## 7.2 配套案例（example）

来源：server.mjs:56–62

```text
示例块：给一个与课程目标直接相关、可复现的完整例子。
用 ## 小标题区分“场景与输入”“分步操作/推理”“预期结果”“为什么这样做”；操作步骤使用编号列表。
少量 **加粗** 标出关键输入、结论或判断点，数据对比适合时使用 Markdown 表格；代码放在标明语言的代码围栏中，公式使用行内代码，逐步解释关键行，并说明前提与边界。
只描述预期结果，不声称已经执行代码或验证外部系统。
```

## 7.3 动手实践（practice）

来源：server.mjs:56–62

```text
实践块：给学习者一个可以独立完成的小任务，写清起点、操作步骤、完成标准和两个由浅入深的提示。
任务应可在普通学习环境中完成，不依赖本应用执行代码。
不要直接交出完整答案；提醒一个常见错误和自查方法。
```

## 7.4 随堂测验（quiz）

来源：server.mjs:56–62

```text
测验块：生成 2–4 道四选一单选题，覆盖概念理解与情境应用，不只考术语记忆。
每题只能有一个明确正确答案；错误选项要对应常见误解，不用“以上皆是”。
answer 必须是正确选项的 0–3 整数下标；explanation 要说明正确原因，并点出容易误选的原因。
```

## 7.5 课程总结（summary）

来源：server.mjs:56–62

```text
总结块：用 3–5 条简短结论提炼本课已讲的知识，包含一个易错点和一个能迁移到新情境的判断方法。
指出下一步可练习什么，不添加前文未解释的新概念。
```

## 10. 实际输入、校验与参数

| 阶段或字段 | 输入范围 | 对质量的影响 |
| --- | --- | --- |
| 学习路线 | goal、level、daily、days、可选 learningBrief | learningBrief 含初步 summary、用户 answers 的 selected/detail、用户 notes |
| 单课大纲 | goal、level、title、objective、可选 learningBrief、route、lessonPosition | route 只有各课标题与目标；没有前面课程正文；没有本课 minutes |
| 当前内容块 | goal、level、title、objective、minutes、intro、block、可选 learningBrief、outline、previous、related、sequence | minutes 是整课时长；没有单块预算；没有整条 route |
| previous | 最近 3 个已生成非测验块，每块正文开头最多 1000 字 | 不保证保留完整概念、步骤与结论 |
| outline | 当前块前后各最多 12 块，加当前块 | 仅 type、title、objective，无正文 |
| related | 生成讲解时，紧随其后的已生成案例，最多 2 个 | 每个开头 2000 字；生成案例时没有此字段提供的配套讲解全文 |
| intro | 导语前 2000 字 | 不等于完整课程背景 |

来源：public/blocks.js:26–39、public/app.js:1375–1387。

结构校验边界：

- 路线检查 3–12 课、完整字段、总时长、重复标题与目标；不证明先修关系与教学安排合理。
- 大纲检查 2–20 块、有效类型与字段、至少一个 reading 和 quiz；没有强制检查每个 reading 后紧接 example，也不强制实践与总结。
- 测验提示要求 2–4 题，但校验接受 1–5 题；校验确认字段完整与下标范围，不证明唯一正确答案。
- 非测验正文 text 最多 12000 字符；现行正文生成提示没有显式告知模型这个上限。

llm.mjs 的调用参数：temperature 固定 0.3；maxTokens 默认 8192，可配置，允许范围 128–32768；连接测试单独用 128。Ollama 请求 think=false；千问请求 enable_thinking=false；DeepSeek 请求 thinking.type=disabled。JSON 模式按配置启用。输出因长度被截断时会报错，没有自动续写。

这些输入与参数同样影响生成质量，提示词无法补回没发给模型的材料。

## 12. 提高首次生成质量的优化建议

以下为依据当前实现提出的候选改法，尚未应用。

### 12.1 优先补齐前文与测验、总结的上下文

要求“承接前文、不重复定义”，但模型只看到最多 3 块开头节选。后面的测验与总结可能看不到课程前半段的实际教学内容；用户还能先生成案例或测验，再生成讲解。

建议给案例显式提供对应讲解；给测验与总结提供本课已生成内容的关键概念、结论、实践和误区摘要。未生成内容明确标记，不能把规划内容当作已讲授内容。这需要调整上下文，仅增加提示不够。

### 12.2 从排版要求转向教学内容要求

现有讲解规则花了较多篇幅规定标题、加粗、列表。建议加强“是什么、为什么成立、何时使用、怎么判断结果”；新术语不能用另一批未解释术语定义。零基础补齐必要前提，进阶避免重复通用常识。不要为所有概念强制套同一个长模板。

### 12.3 对齐案例、实践与测验的目标

案例演示关键方法，实践迁移同一方法，测验检验核心判断与误区。避免把未讲知识作为正确作答的必要条件。生成测验前先独立求解，核对选项、answer、explanation，检查其他选项是否在题设下也成立。只输出最终内容。

模型自检不等于独立事实核验，应继续保留独立评审。

### 12.4 把整课预算落实到模块

大纲没有 minutes，正文却用整课 minutes 控制单块篇幅，多个块可能各按整课预算扩写。建议先把本课时长传给大纲，再为模块分配阅读、操作、练习时间。新增字段须同步更新验证、保存和展示，不能仅要求模型多返回字段。

可先补充：“minutes 是整节课的总时长，当前块只占其中一部分；只写实现 block.objective 所需内容。非测验 text 最多 12000 字符。”字符上限不能代替教学时间预算。

### 12.5 消除代码围栏规则的歧义

公共规则“不要代码围栏”与正文规则“代码用代码围栏”可能冲突。建议明确：“根输出为可解析 JSON，禁止在 JSON 外添加解释或包裹整个 JSON 的 Markdown 围栏；正文字符串内部允许任务规定的 Markdown 和程序代码围栏。”这个改动不需要改变现有 JSON 字段。

### 12.6 让校验与提示承诺一致

如“每个讲解后紧接案例”“测验 2–4 题”是必须满足的产品规则，结构校验也应检查；如 1–5 题是刻意保留的弹性，应统一说明。

建议先优化第 7 节的共同要求与五类教学规则，再处理上下文、课时分配。保留现有五类内容块和 JSON 字段，便于比较。

## 13. 共同教学规则的补充草案

以下是供逐句审阅的候选文字，尚未启用。可放在内容块共同规则中、类型规则之前。需要完整教学材料的约束应配合上下文改进。

```text
目标对齐：只讲支撑 block.objective 的必要知识和方法。读完应能做出具体解释、判断或操作，不以术语堆砌代替教学。
难度适配：以 level 与用户确认的 learningBrief 为起点，不自行假定工具、环境和先修知识已具备。首次使用必要术语时用易懂的话定义，并说明在当前任务中的作用。
解释深度：对关键结论说明成立条件与理由；对方法说明何时使用、如何判断结果。复杂过程分步展开，省略与当前目标无关的扩展内容。
内容一致：使用上下文中一致的术语、符号和案例条件。只有实际提供的已生成正文才能视为已讲授内容；不能声称未提供的信息前文已经解释或学习者已经掌握。
可复现性：案例输入、前提、步骤和预期结果相互一致；代码说明必要环境和依赖，不编造运行结果。实践给完成标准与自查方法，提示逐步递进，保留独立完成的空间。
生成前检查：目标是否覆盖、前提是否说明、术语是否定义、推理与数字是否一致、是否引入本块不需要的概念。测验另检查唯一答案、下标和解析一致。只输出最终内容，不输出检查过程。
篇幅控制：minutes 是整课总学习时间，当前块只占一部分。优先保证关键解释和目标覆盖，删除重复导语和泛泛鼓励。非测验 text 最多 12000 字符。
```

## 14. 如何验证优化效果

固定同一模型与参数，对相同需求比较原提示和候选提示。样例覆盖零基础与进阶、编程与非编程、明确与宽泛目标、短与长课时。

检查首次结构通过、讲解与案例一致、测验覆盖已讲内容、实践能否完成、未定义术语与内容过量。不要仅比较长度或模型自评分；结合独立评审和人工阅读。当前没有执行真实模型比较。
